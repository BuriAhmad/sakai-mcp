# Deployment paths

- `infra/` defines the Azure development resources and staged MCP Container Apps templates; see `infra/README.md`. The existing `scripts/deploy-infra.sh` remains the Sakai VM/MySQL path and does not apply the MCP templates.
- `configure-vm.sh`, `configure-sakai.sh`, and `deploy-sakai.sh` document the **original Sakai 25.2 bootstrap**. `deploy-sakai.sh` intentionally refuses a modified source checkout.
- `configure-tomcat-proxy.sh` is the repeatable Tomcat reverse-proxy configuration used by `configure-vm.sh`. It binds the HTTP connector to loopback and trusts forwarded HTTPS scheme information only from local Nginx. For an existing VM, run it through `./sakai shell 'bash -s' < deployment/configure-tomcat-proxy.sh`, restart Tomcat, then check public `/portal` and an authenticated form action. It saves the previous `server.xml` once as `server.xml.pre-mcp-proxy` for configuration rollback.
- `ensure-sakai-java-opens.sh` adds the Java module options required by the tracked Sakai 25.2 Docker runtime and used by its tests. `configure-vm.sh` calls it after writing `setenv.sh`. On an existing VM, run `./sakai shell 'bash -s' < deployment/ensure-sakai-java-opens.sh`, restart Tomcat, and check the affected tool UI and public `/portal`. It saves the previous `setenv.sh` once as `setenv.sh.pre-mcp-java-opens`.
- `configure-mcp-sakai.sh` writes a marked, repeatable MCP block to the VM's runtime-only `local.properties`; it saves the original once as `local.properties.pre-mcp`. It takes `true|false TENANT ISSUER AUDIENCE sakai.mcp.access JWKS_URI`, all obtained from issued downstream tokens/tenant metadata. Stream the tracked script through `./sakai shell 'bash -s -- true ...' < deployment/configure-mcp-sakai.sh` only after Phase 7 validation; then use the guarded exact-commit release for restart. The flag is disabled by default in code. It was applied for the Phase 8 development release; see [the Sakai adapter documentation](../docs/mcp/sakai-adapter.md) and [sanitized release result](../docs/evidence/mcp/phase-8-release.md).
- `release-sakai-vm.sh` is the guarded, code-only release and rollback procedure for later commits. Do not invoke it by hand; use the root `./sakai deploy COMMIT` and `./sakai rollback RELEASE_ID` commands, or the manual GitHub Actions deployment workflow.
- `run-course-site-layout-migration.sh`, invoked by `./sakai migrate-course-layout`, applies course layout v2 (including Lessons and two-column Overview) and the Student `roster.viewallmembers` grant to only the Course A/B IDs in ignored `deployment/mcp-test-sites.env`. It also configures that grant in the course authorization template for future courses, using AuthzGroupService. It preserves the prior runtime properties file, locks against concurrent releases, enables the scoped Quartz job for one restart, and clears the temporary trigger on success or failure. Run only after an explicitly requested resume and exact-commit code deployment; see [course defaults](../docs/COURSE_SITE_DEFAULTS.md).
- `release-mcp.sh` is the MCP image publication, revision update, and post-deploy smoke procedure. The manual `deploy-mcp.yml` workflow builds/scans an exact commit, then invokes it in `bootstrap` mode to push a first immutable image or `deploy` mode to update an existing app. `check-only` builds and scans without Azure access. The Phase 18 foundation and initial app now exist. Follow [the MCP release guide](../docs/MCP_RELEASES.md) for release and revision rollback. This script never changes the Sakai VM or MySQL.

Read [the release runbook](../docs/SAKAI_RELEASES.md) before a first release. The release script stops Tomcat for the build, keeps a rollback copy of application directories, and does not alter the database, uploads, or `local.properties`.
