# Building and releasing the development MCP service

The MCP service has its own manual release path. A push to `main` validates its Python package, protocol/security tests, source and dependency scan, container build, and image scan. It does not deploy Sakai or MCP. Sakai continues to use `./sakai deploy COMMIT` and `./sakai rollback RELEASE_ID`.

## Exact-commit check

The [Build or deploy MCP](https://github.com/BuriAhmad/sakai-mcp/actions/workflows/deploy-mcp.yml) workflow accepts one full commit SHA on `main`. Run it with `check-only` first. It archives `services/mcp/` from that exact commit, installs locked production dependencies into a non-root Python 3.11 image, and runs the pinned Trivy scanner against the source/lockfile and image. Its source archive contains no local credentials or test-user files. The scanner reports counts only; detailed results stay on the disposable runner. The workflow's `deploy` choice repeats the build and scans, then uses the existing `sakai-dev` GitHub/Azure federated identity. No long-lived Azure client secret is used.

Locally, `scripts/build-mcp-image.sh services/mcp sakai-mcp:local FULL_COMMIT_SHA` exercises the same build and scan path. The image labels record the source commit and SHA-256 of `uv.lock`. The final runtime image has no build tooling, runs as UID/GID 10001, and has no certificate or private key baked in. Scanner image and Python base image are pinned by digest. A high or critical finding with an available fix, a critical finding without a fix, or any detected secret fails the gate. High findings without published fixes are counted and must be recorded in the phase evidence and reviewed when the base digest is updated.

## Azure deployment and revision workflow

Phase 18 completed the initial foundation and app deployment, Key Vault credential placement, and scoped role grants. See [`evidence/mcp/phase-18-runtime.md`](evidence/mcp/phase-18-runtime.md) for that dated deployment record. Before any later release, verify the selected subscription and current Azure state, then use the workflow below. The app's public URL, Entra metadata, Sakai origin, secret references, identity, ingress, probes, and scaling remain defined by the app template. Its `sourceCommit` and `lockSha256` parameters must match the image labels. Do not use the Sakai VM deployment script for MCP.

The `bootstrap` mode builds, scans, and pushes an exact-commit image before a Container App exists, then prints its immutable digest and lock SHA-256. It was used for the initial Phase 18 deployment and remains the bootstrap path if a new app must be created. Preview and apply `mcp-app.bicep` with that digest and matching source/lock values. For the existing app, use `deploy` for later workflow-driven revisions. Bootstrap uses the same GitHub scan gate as `check-only` and `deploy`.

The canonical public endpoint and protected resource identity are both `https://mcp.smartdigest.app/mcp`; `MCP_PUBLIC_URL` remains the HTTPS origin `https://mcp.smartdigest.app`. Its CNAME must point directly to the Container App's generated FQDN with Cloudflare proxying disabled. Azure's hostname/certificate bootstrap is a prerequisite after the domain-ownership TXT record is published: run `az containerapp hostname add`, then `az containerapp hostname bind --validation-method CNAME` for the app/environment. Azure provisions a managed environment certificate asynchronously. Once it is `Succeeded`, the steady-state `mcp-app.bicep` declares the SNI binding and references the Azure-managed certificate by its resource name. The generated Azure hostname remains the backend ingress FQDN.

The MCP Entra registration includes the path-based `https://mcp.smartdigest.app/mcp` Application ID URI and requests v2 access tokens. The previous origin URI remains registered for rollback. For Entra v2, `MCP_AUDIENCE` is the MCP app client ID GUID; the resource URI remains the OAuth resource indicator and protected-resource metadata identity. Keep `MCP_ISSUER` and `MCP_JWKS_URI` tenant-specific v2 endpoints. Sakai remains a separate v1 resource and issuer, configured with `SAKAI_ISSUER` and its own audience. Preserve this distinction when deploying or changing Entra token-version settings.

Phase 18 granted the existing federated GitHub deploy principal AcrPush on the MCP ACR and Container Apps Contributor on `ca-mcp-sakai-dev`, scoped to those resources. Confirm required grants and the `sakai-dev` environment restriction to `main` before a later release. The release script refuses a wrong subscription, missing app, ambiguous registry inventory, or an image whose labels disagree with the selected commit. It pushes the scanned image and resolves its ACR SHA-256 manifest digest before calling `az containerapp update` with that immutable digest. It sets `APP_COMMIT` and `APP_LOCK_SHA256` for audit correlation, then checks TLS-backed `/live`, `/ready`, unauthenticated Bearer challenge, canonical protected-resource metadata, selected digest, revision readiness, SNI binding, and disabled affinity. It does not change Sakai.

The workflow's `check-only` mode passed on [2026-09-27](https://github.com/BuriAhmad/sakai-mcp/actions/runs/36322365794). That was a Phase 17 result; Phase 18 subsequently deployed the app using `bootstrap` and the reviewed Bicep templates. A successful `check-only` still does not deploy a service.

## Revision rollback

The release output records the previous digest and new revision. If a new revision must be reverted, inspect `az containerapp revision list -g rg-sakai-mcp-dev -n ca-mcp-sakai-dev`, select the last verified ready revision, and create a new revision from it with `az containerapp revision copy -g rg-sakai-mcp-dev -n ca-mcp-sakai-dev --from-revision REVISION_NAME`. Recheck the same HTTPS health, OAuth, and authenticated tool behavior. This changes only the MCP Container App revision; it does not undo announcements or Sakai runtime state. The Container App retains up to three inactive revisions, so record a known-good digest before the retention window expires.
