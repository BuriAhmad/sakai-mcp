# Phase 7 — Sakai adapter progress (2026-09-26)

Status: **IN PROGRESS; local source and focused-test checks PASS; deployment gate NOT RUN**.

The implementation is confined to tracked Sakai WebAPI source. The outer Sakai `RequestFilter` remains first. A second filter maps only `/mcp/v1/*` (within the `/api` webapp) and is disabled by default. It requires a secure request and bearer token, validates the signature against a configured HTTPS Entra JWKS with an RS256 allowlist, checks configured issuer/tenant/downstream audience/scope and token times, and requires the observed singleton-array `extn.SakaiEid`. It does not accept caller identity headers or a website cookie as authentication for the MCP path.

After verification, the filter invokes Sakai 25.2 `AuthenticationManager.authenticate(ExternalTrustedEvidence)` to resolve AID/EID and reject disabled users. It compares the resolved EID to the token identifier, creates a separate Sakai session, calls `UsageSessionService.login`, and restores the previous request session after invalidating only the delegated session in a `finally` block. Focused tests were added for cryptographic rejection, claim rejection, cookie-only access, identity mismatch, and success/exception cleanup.

The five V1 Sakai routes are now implemented: current-user course listing, own grades, visit-gated visible announcements, assignment/site-and-group-checked submission metadata, and permission-checked plain announcement creation. The write path uses only the site's main channel, sets the current Sakai user as author, and makes one commit attempt. It has no automatic retry or assignment-deadline mutation.
