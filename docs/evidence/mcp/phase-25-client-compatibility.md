## Empirical client diagnostic

The actual published Inspector **2.8.0 CLI** was run with modern 2026-07-28 era against an ephemeral localhost proxy forwarding unchanged MCP bodies/headers to `https://mcp.smartdigest.app/mcp` and injecting a fresh synthetic Student A bearer in memory. `tools/list` exited 0 and returned exactly the fixed five V1 names. A `list_my_courses` call later exited 0 and returned a successful nonempty structured course result. The first attempted read returned a proxy-side HTTP 500, then the retry of this **read-only** operation succeeded; the diagnostic bridge was not counted as an OAuth or reliability acceptance result. The local proxy was stopped afterward. No write was issued by Inspector.

The proxy deliberately bypassed Inspector's own OAuth flow, so this demonstrates only CLI transport/catalog/read behavior with a pre-obtained delegated token. It does **not** establish native client connection/authentication, approval display, Cancel/Reject, Allow/exactly-one create, persistent allow, or autonomous-mode behavior. Inspector is not claimed as an approval-enforcing host. No compatibility claim is made for Claude, Claude Code, OpenCode, or ChatGPT.

## Path-based resource correction (2026-09-29)

After account selection, the human again received `AADSTS9010010`. Read-only inspection found that Entra registered the MCP Application ID URI as `https://mcp.smartdigest.app`, while the installed Inspector 2.8.0 OAuth library converts protected-resource metadata into a JavaScript `URL` and serializes the origin as `https://mcp.smartdigest.app/` when sending the OAuth `resource` parameter. [Microsoft's MCP/Entra guidance](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id#i-get-error-aadsts9010010-when-a-client-requests-a-token-for-my-mcp-server) says this trailing slash differs from the Application ID URI and causes `AADSTS9010010`. Inspector's locally stored discovery state also still contained the earlier bare `mcp.access` scope; it must be cleared before retrying. The actual failed authorization request parameters were not captured, so the slash diagnosis is based on verified Inspector request-construction code, Entra registration, and the observed error.

With the human's approval, the existing MCP resource app gained the additional Application ID URI `https://mcp.smartdigest.app/mcp`; its prior root and `api://` identifiers were retained. The resource still issues v2 tokens and exposes only the existing delegated `mcp.access` scope. The existing Inspector test client retained its same sole scope grant and loopback callbacks. Commit `4065faaa1cf280946581069cab2a9158209f3f90` derives the OAuth resource from the fixed `/mcp` endpoint, updates its protected-resource metadata and Bearer challenge, and aligns the server's token-resource and OBO checks. The public origin and Sakai configuration did not change.

The [exact-commit MCP release](https://github.com/BuriAhmad/sakai-mcp/actions/runs/36528150871) passed its build, scans, revision update, health, challenge, and metadata checks. Azure reports ready revision `ca-mcp-sakai-dev--0000009` at image digest `sha256:938b098240b403b2a40fc741edb49e72d85340cec040b78ab659fd3ebe02e51e`. Live `POST /mcp` without a token returns `401` with `resource_metadata=https://mcp.smartdigest.app/.well-known/oauth-protected-resource/mcp`; that document returns `resource=https://mcp.smartdigest.app/mcp` and `scopes_supported=["https://mcp.smartdigest.app/mcp/mcp.access"]`. A read-only authorization probe with this exact resource, scope, existing client ID, and loopback callback reached Microsoft's sign-in page without `AADSTS9010010` or `AADSTS50011`. This probe did not sign in or acquire a token.

**At this deployment checkpoint, native OAuth remained unproved.** The human still needed to clear Inspector's stored OAuth state, update the saved server's OAuth scope to `https://mcp.smartdigest.app/mcp/mcp.access`, and retry as Student A.
