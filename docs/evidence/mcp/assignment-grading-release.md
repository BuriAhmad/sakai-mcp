# Assignment grading: development release evidence

Date: 13 October 2026. Target: the existing public MCP endpoint `https://mcp.smartdigest.app/mcp`, backed by Sakai development site `F26-CS210-DM` on `vm-sakai-dev` in `rg-sakai-mcp-dev`. The user selected this endpoint for the release. This is a development deployment, not a separate production Sakai environment.

## Released capability

The MCP Container App has `ASSIGNMENT_GRADING_ENABLED=true` and Sakai has `mcp.assignment.grading.enabled=true`. The nine grading tools are added independently of the five default tools and three existing assignment-setup tools, giving a 17-tool authenticated catalog. The MCP revision is `ca-mcp-sakai-dev--0000018`; its image was built from commit `824f1caa590d` and pinned by digest `sha256:5c1079b759f0c1af56dcefbbacee2152296285ca2e8247bec01982ec69a6db4b` in the release. Later fixes in this sequence are native Sakai code and do not require a new MCP image. New environments still default to disabled.

The nine tools are `get_assignment_grading_context`, `list_assignment_submissions`, `get_assignment_submission`, `export_assignment_submissions`, `get_assignment_submission_export`, `save_assignment_grades`, `release_assignment_grades`, `get_assignment_grades`, and `get_assignment_grading_operation`. The repository Skill is [sakai-assignment-grading](../../../skills/sakai-assignment-grading/SKILL.md); an installed copy is in the user's Codex Skills directory. The Skill is local to Codex, while the nine tools come from the MCP catalog. It requires an assignment-specific plan and separate approval of exact official save and return payloads.

Native preparation included a database backup and additive `ASN_SUBMISSION.LOCK_VERSION` migration, owner-only durable `/var/lib/sakai-grading`, its cleanup timer, the CS210 Teaching Assistant `asn.grade` permission, and Sakai's grading property. The Azure subscription was checked before changes. No official grade save or return was performed on live student work.

## Checks and incident

The public MCP catalog exposed 17 tools after release. Delegated instructor calls for grading context, submission roster, submission detail, and selected grade readback succeeded against CS210. Detail included the student attachment; grade readback showed an ungraded row. The original CS210 import report correctly checked 79 submitted files, one intended missing student, a closed deadline, PDF and sample TXT downloads, and zero graded/returned submissions. It did **not** check the student Assignments submission page. Its `PASS` therefore did not establish that page rendered. After the Sakai restart, the legacy Direct API assignment representation returned an empty embedded `submissions` list, although the grading endpoint still returned the live records. The final verifier now uses the dedicated grading roster for those rows.

At 12:28:40 UTC, the affected student submission page failed with `HibernateException: Unable to resolve owner of loading collection AssignmentSubmission.attachments` for submission `6bd32539-4fbe-46a2-935b-567654138e73`. The imported submission had an attached TXT file; the older assignment did not exercise this path. Native grading evidence load was moved into a read-only transaction that hydrates its collections (`10b1561e`), and the student page was changed to use that hydrated load (`36597479`). After the second release, delegated synthetic student `demo26s056` received HTTP 200 with a nonempty inner tool page containing the assignment title and `27100056.txt`; this is the exact affected submission. An ignored local import verifier now checks page content as well as direct downloads.

Live grading roster reads then showed 81 expected, 79 submitted and two missing because the native candidate API included instructor `demo26i002`. Commit `d54bcc13fcc85a5ef8510ac1e2c8514fad5c356b` restricts the grading roster to active course members with submission permission and without grading permission, matching native submitter eligibility. Its focused Java test passed locally; both repository and Sakai source CI workflows passed.

The final guarded Sakai release `20261013T172837Z-d54bcc13fcc8` completed successfully from that exact commit. Local and public portal health checks passed. Live MCP readback reports 80 expected students, 79 submitted, one missing (`demo26s060`), zero drafts, zero graded and zero returned. The exact student Assignments page returned HTTP 200 with the assignment title and `27100056.txt`; that file and the student-facing PDF both downloaded byte-for-byte against the ignored local package. The final ignored report is `deployment/artifacts/cs210-mcq-import/final-verification.json` with status `PASS`. The artifact directory contains 122 files and none are tracked by Git.

The VM was deallocated by its existing 19:00 Asia/Karachi auto-shutdown before the final roster release. It was started as part of the user-authorized deployment, and the existing single-address SSH allowlist was refreshed. Generated Maven `target` directories from the previous release source tree were removed to recover build space; deployed binaries, backups, source and database were preserved. `./sakai deploy` builds a guarded pushed commit and restarts Tomcat, causing temporary Sakai unavailability. No VM was recreated and no Azure infrastructure template was reapplied.
