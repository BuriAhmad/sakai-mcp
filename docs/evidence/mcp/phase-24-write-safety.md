# Phase 24 — announcement write safety and retry behavior (2026-09-28)

Status: **PASS**. Live tests used the unchanged MCP source `d1b32280c3ca0bfc590b51d95d8adf667ecd293f`, revision `ca-mcp-sakai-dev--0000004`, and the existing Sakai release. Only synthetic sandbox announcements were sent. An ignored local operation journal recorded each intended request before its single POST; it is outside Git and no ambiguous operation was retried.

The deployed 2026-07-28 MCP probe passed **11/11** checks. Before writing, unique synthetic titles were absent. Student A's Course A create and Instructor A's Course B create each returned `FORBIDDEN`; subsequent authorized reads found zero corresponding objects. One authorized Instructor A Course A create returned a created ID; Student A's announcement read found that ID exactly once. Two further intentional requests used identical title and body, returned distinct created IDs, and the Course A announcement read found exactly those two objects. The first authorized title remained singular. This demonstrates that same content is not falsely deduplicated. The ordinary authenticated Sakai Course A portal returned HTTP 200 and rendered the authorized and repeated synthetic titles, while the denied titles were absent. The portal repeats title text in markup, so authoritative object counts came from distinct announcement IDs in Sakai's narrow read response.

The Sakai write controller makes one `addAnnouncementMessage`/`commitMessage` attempt. The MCP adapter sets `attempts = 1` for POST, unlike bounded GET retries. An existing timeout/5xx/malformed-response test already verified `AMBIGUOUS_WRITE_OUTCOME` and one POST attempt. This phase added a focused mock-transport test that simulates a committed announcement followed by a lost response: the adapter returns `AMBIGUOUS_WRITE_OUTCOME`, makes exactly one POST, and a subsequent read finds the single committed object. A pre-connect failure remains a dependency error with one attempt. The full current MCP suite passed **41/41**, Ruff and mypy passed. No content-based deduplication or automatic write replay was introduced. The project has not established a durable Sakai operation marker; a real ambiguous outcome must be surfaced and the state inspected before a human/client makes a separate retry decision.

The existing Container Apps Log Analytics sink showed four created-object audit references in the most recent hour (the Phase 22 write plus these three successful Phase 24 writes). A bounded query found zero occurrences of the synthetic Phase 24 title prefix, bearer/access-token markers, announcement `body` JSON keys, or private-key markers in console records. Audit contains hashed created/site references and outcomes, not announcement text. This query covers the observed window, not every future error path. Client-side approval/cancellation is a separate Phase 25 gate and is not claimed here.
