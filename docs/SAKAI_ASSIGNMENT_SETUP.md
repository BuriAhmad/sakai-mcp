## Product workflow and decisions

An instructor says, “Set up Assignment 3 for CS202 from this PDF. Release it Monday, give students two weeks, make it worth 100 marks under the Assignments category, and announce it.” The agent reads the brief as content, resolves the actual site, inspects assessment state, derives a single plan, surfaces material ambiguities/conflicts, obtains approval, executes dependencies, verifies, and reports IDs and remaining work.

On 8 October 2026 in Asia/Karachi, the upcoming Monday is 12 October and fourteen calendar days later is 26 October. **09:00 and 23:59 are not supplied by that request.** Use a verified course convention or ask about those times; show resolved dates/timezone in the proposal. Fourteen days at the same time differs from a due date at end of day. The PDF is input for instructions; “from this PDF” does not automatically authorize storing the original PDF as a Sakai attachment.

The plan contains site ID/title, instructions or a faithful preview, visible/open/due/accept-until instants, points, submission mode, resubmission count/deadline, publication state, existing category ID, grade-item release/counting flags, calendar deadline choice, attachment references, announcement content/timing, warnings and the context observation time. Keep explicit academic policy from the brief; never change weights, grade structure or grading policy to fit an assumption.

Draft-first staging belongs inside the coordinator: a published create must not expose a usable assignment until its requested linked objects are verified. Detect these requests and report unsupported capability; do not silently drop them. Native Sakai supports more than this slice.

## Existing implementation and reusable boundaries

[Python server](../services/mcp/src/sakai_mcp/server.py) registers tools inside `create_server`, annotates reads/writes and calls `audit_call`. Its five-tool catalog is static, not role-filtered. [Sakai client](../services/mcp/src/sakai_mcp/sakai_client.py) validates bounded inputs, quotes IDs as single URL segments, performs OBO, calls a fixed origin and returns typed error codes. It retries GET up to three times, POST once; write timeout/5xx/bad response can be `AMBIGUOUS_WRITE_OUTCOME`. `X-Correlation-ID` is an audit correlation, **not** a durable operation marker. Payload typing currently assumes `dict[str, str]`; nested contracts need explicit typed models/general JSON typing and response validation.

Use [auth.py](../services/mcp/src/sakai_mcp/auth.py), [obo.py](../services/mcp/src/sakai_mcp/obo.py), [McpBearerFilter](../apps/sakai/webapi/src/main/java/org/sakaiproject/webapi/mcp/McpBearerFilter.java) and [adapter/auth docs](mcp/sakai-adapter.md) unchanged as the identity authority: validated MCP principal → distinct OBO token → verified canonical `extn.SakaiEid` → isolated Sakai request session. Never accept caller identity, credentials, arbitrary URL, admin fallback or privileged seeding session. The bearer filter applies only to `/api/mcp/v1/*`; legacy SOAP and `/direct/` do not automatically accept that token.

Every proposed route first uses `SiteService.getSiteVisit`, requires a course, checks the native permissions for each selected operation, and validates assignment/item/category/resource/calendar ownership. Effective permissions, not the string “Instructor”, determine eligibility. A TA with grading rights alone is not necessarily allowed to add/revise assessments. Return caller capability flags for planning; recheck on writes. Full context should require `AssignmentService.allowAddSiteAssignment` and `GradingService.currentUserHasEditPerm` for the initial site-wide slice. Deny unauthorized context rather than leaking unpublished assessment metadata; calendar read may instead be unavailable with an explicit reason.

Human approval is a host/client policy separate from Sakai authorization. This Skill requires an approved coherent write plan. Tool annotations do not prove approval; do not add a server `human_approved` boolean, server elicitation or an approval claim to audit. A host may require approval per call despite workflow approval. The real LLM host Allow/Cancel/persistent-allow/autonomous-mode experiment remains open in Phase 25; Inspector manual execution is not that evidence.

## Source and interface research

### Assignment model, reads and mutation

**Partially confirmed — source:**

- [AssignmentService](../apps/sakai/assignment/api/src/java/org/sakaiproject/assignment/api/AssignmentService.java): `allowAddAssignment`, `allowAddSiteAssignment`, `allowUpdateAssignment`, `addAssignment`, `getAssignment`, `getAssignmentsForContext`, `updateAssignment`, `deleteAssignmentAndAllReferences`.
- [AssignmentServiceImpl](../apps/sakai/assignment/impl/src/java/org/sakaiproject/assignment/impl/AssignmentServiceImpl.java): `addAssignment` persists a skeletal object after `asn.new`; it does **not** execute the UI's Gradebook, calendar and announcement creation logic. `updateAssignment` checks `asn.revise`, updates modification metadata and a task via `TaskService`; a Task is not proof of a Calendar event. Method-level `@Transactional` does not prove an orchestration transaction across Gradebook, calendar and notification systems.
- [Assignment model](../apps/sakai/assignment/api/src/java/org/sakaiproject/assignment/api/model/Assignment.java): separate `draft`, `deleted`, `visibleDate`, `openDate`, `dueDate`, `closeDate`, `dropDeadDate`, `scaleFactor`, `maxGradePoint`, `releaseGrades`, audience/group fields, properties and attachment references.
- [AssignmentAction](../apps/sakai/assignment/tool/src/java/org/sakaiproject/assignment/tool/AssignmentAction.java): `post_save_assignment`, `commitAssignment`, `editAssignmentProperties`, `updateGradebookIntegrationProperties`, `integrateAssignmentWithGradebook`, `integrateWithCalendarTool`, `integrateWithAnnouncement` are the native workflow reference. Much orchestration is private and depends on tool `SessionState`; do not instantiate a tool action or invent a current placement from WebAPI.
- [AssignmentEntityProvider](../apps/sakai/assignment/tool/src/java/org/sakaiproject/assignment/entityproviders/AssignmentEntityProvider.java): `GET /direct/assignment/site/{siteId}.json` (existing seeding read **Confirmed**), item/submission/grade/announcement linkage actions. Implements `Inputable` but not general `Createable`/`Updateable`; no generic `createEntity` method. Input support is not evidence of assignment POST CRUD. `SimpleAssignment` resolves numeric Gradebook items and external IDs; its DTO includes submissions, so the proposed context must build a smaller metadata DTO rather than return it wholesale.
- `getAssignmentsForContext` applies draft ownership/`asn.share.drafts` and group permissions. Its results can omit another instructor's draft. Context completeness must indicate permission scope, not promise all site assignments. Duplicate preflight alone cannot guarantee uniqueness across hidden drafts.

Native submission enum indexes: 0 none, 1 text only, 2 attachment only, 3 text and attachment, 4 non-electronic, 5 single attachment, 6 external tool, 7 video. The proposed stable strings map only to 1–5. A report PDF plus source archive requires attachment-only or text-and-attachment, **not** single attachment. Mode does not enforce requested filenames, MIME types or number of files beyond native single attachment; describe such requirements in instructions unless a separate validated feature exists.

Native grade enum indexes: 0 none, 1 ungraded, 2 letter, 3 score, 4 pass/fail, 5 check. Initial contract fixes score grading; do not present `max_points` for every grade type. `getScaleFactor()` uses `10^assignment.grading.decimals`, default factor 10. Store 100 points as `maxGradePoint=100*scaleFactor`, with exact decimal arithmetic, integral/Java-integer overflow checks and no rounding. Read back `maxGradePoint/scaleFactor`. SOAP's fixed division by ten is insufficient when decimals differ.

Publication, preview visibility, opening submissions and releasing grades are separate. `dueDate` marks the due deadline; `closeDate` controls accept-until and late submission window; `dropDeadDate` is assigned dueDate by the native UI but is not an agent-facing substitute for closeDate. Native UI supports no close date; several submission code paths dereference `closeDate`, so **null-close acceptance is unverified**. Initial contract requires finite `open_at <= due_at <= close_at`, with open strictly before due. Same due/close means no late window. Visibility defaults to open in the proposed adapter, explicit `visible_at` may precede it. Do not equate posted-but-future-open with currently available.

`ALLOW_RESUBMIT_NUMBER` stores string 0/absent (disabled), positive counts or -1 (unlimited); `ALLOW_RESUBMIT_CLOSETIME` stores epoch milliseconds. `canResubmit` uses the later of assignment close and resubmit close in a finite-close case. Initial validation requires enabled resubmit deadline at least closeAt to avoid silently extending a requested earlier limit; unlimited count still has a finite deadline. Submission-level overrides remain out of scope.

**SOAP alternative — Partially confirmed:** [Assignments.java](../apps/sakai/webservices/cxf/src/java/org/sakaiproject/webservices/Assignments.java) exposes RPC/literal `createAssignment(sessionId, gradebookUid, context, title, dueTime, openTime, closeTime, maxPoints, gradeType, instructions, subType)` on `/sakai-ws/soap/assignments?wsdl`; [CXF registration](../apps/sakai/webservices/cxf/src/resources/applicationContext.xml) also exposes `GET /sakai-ws/rest/assignments/createAssignment`. Times are epoch milliseconds; returns assignment ID **or exception text**. It sets draft=false, dropDead=due, individuallyGraded=true and releaseGrades=true; always attempts external Gradebook integration, uses maxPoints/10, has no category/resubmission/visibility/attachment arguments, and adds a zero-duration `Deadline` if main Calendar is found. It does not persist the native bidirectional Calendar link in that block. Its copied Gradebook helper can silently swallow errors or suffix a conflicting title. An assignment ID is therefore not proof of coherent setup. Do not adopt mutation-via-GET or this legacy orchestration for the proposed MCP contract.

### Assignment ↔ Gradebook and grade model

**Partially confirmed — source:**

- [GradingService](../apps/sakai/gradebookng/api/src/main/java/org/sakaiproject/grading/api/GradingService.java): `getGradebookInformation(uid, siteId)`, `getAssignments(uid, siteId, SortType)`, `getCategoryDefinitions(uid, siteId)`, `currentUserHasEditPerm`, `addAssignment`, `updateAssignment`, `addExternalAssessment`, `getExternalAssignment`, `updateExternalAssessment`, `removeExternalAssignment`, group Gradebook discovery.
- [GradingServiceImpl](../apps/sakai/gradebookng/impl/src/main/java/org/sakaiproject/grading/impl/GradingServiceImpl.java): standalone `addAssignment` returns numeric ID and checks assessment-edit permission; `addExternalAssessment` returns void, validates title/external ID/points/category, sets externallyMaintained=true and released=true. Its body does **not** establish the same actor edit permission as standalone add. The endpoint must explicitly check permissions before calling trusted external integration methods.
- [GradingAuthz](../apps/sakai/gradebookng/api/src/main/java/org/sakaiproject/grading/api/GradingAuthz.java): `gradebook.editAssignments`, grader/student and section capabilities. Require assessment edit plus assignment add/revise, not just `currentUserHasGradingPerm` as the UI helper does.
- [AssignmentToolUtils](../apps/sakai/assignment/tool/src/java/org/sakaiproject/assignment/tool/AssignmentToolUtils.java): `integrateGradebook` and `removeNonAssociatedExternalGradebookEntry`; package-private, placement-dependent fallback, alert lists and some swallowed exceptions. Extract service-level coordination or call the underlying services with explicit site/permission checks, not this UI helper directly.
- [Gradebook Assignment DTO](../apps/sakai/gradebookng/api/src/main/java/org/sakaiproject/grading/api/Assignment.java), [GradebookAssignment entity](../apps/sakai/gradebookng/api/src/main/java/org/sakaiproject/grading/api/model/GradebookAssignment.java), [CategoryDefinition](../apps/sakai/gradebookng/api/src/main/java/org/sakaiproject/grading/api/CategoryDefinition.java), [GradebookInformation](../apps/sakai/gradebookng/api/src/main/java/org/sakaiproject/grading/api/GradebookInformation.java), [GradingConstants](../apps/sakai/gradebookng/api/src/main/java/org/sakaiproject/grading/api/GradingConstants.java) define settings and normalized metadata.

Category mode: native 1 no categories, 2 categories only, 3 weighted categories. Grade entry type points/percentage/letter is a separate setting, not category mode. `CategoryDefinition.weight` is fractional (0–1); normalize to `weight_percent` **on categories only**. `getAssignmentDefinition` populates item DTO `weight` from its category's weight. It is not an independent item write parameter.

Within a category, equal weighting averages normalized item scores; otherwise maxima contribute to points weighting. Drop-lowest/drop-highest/keep-highest and extra credit can change contributions. Do not calculate a guaranteed course percentage from points alone. Category drop rules with unequal maxima can reject an item (`addExternalAssessment` checks points mismatch when drop scores and no equal weighting). Category association must belong to this Gradebook and be active; prevalidate missing categories because some implementation branches dereference a missing category before producing `InvalidCategoryException`.

Item `released`, item `counted`, category membership, course-grade visibility and `displayReleasedGradeItemsToStudents` are distinct. External add sets released=true; explicitly stage it unreleased, then apply approved release/counting flags using a fully populated definition through permission-checked `updateAssignment`. Preserve external ownership fields; do not send a sparse DTO that clears them/category. Its generic update leaves external item's name/points/due owned by the external service but permits category/release/counting edits. Grade scores remain unreleased in Assignments (`releaseGrades=false`); grade-item visibility does not authorize publishing scores.

Native Assignment integration supports:

1. No Gradebook.
2. Add an external item: external ID is `AssignmentReferenceReckoner`'s assignment reference, external app is the Assignment tool ID, gradableReference is the assignment reference, category supplied by ID. Lookup `getExternalAssignment(uid, reference)` after void create to obtain numeric item ID. Persist Assignment integration properties using the native `updateGradebookIntegrationProperties` semantics: posted ADD becomes ASSOCIATE with the assignment reference in `PROP_ASSIGNMENT_ASSOCIATE_GRADEBOOK_ASSIGNMENT`.
3. Associate an existing item: the Assignment property can contain numeric item ID or external reference; native group Gradebooks allow comma-separated associations. Title matching is not linkage. UI supports association after creation, but ownership, sharing, scores and mismatched points require care. Initial MCP slice supports **new external item or none only**; an existing similarly named item is a conflict, not permission to adopt it. A future `existing` mode needs a separate explicit approval and tested rules for scores/other owners/maxima.

Native UI integrates only when posting. `AssignmentService.addAssignment` alone does not create a Gradebook item. Later Assignment edits drive external points/title/due updates; edit these through the owning component, not standalone Gradebook create. Shared associations and deletion are not safe compensating actions: native `deleteAssignmentAndAllReferences` removes linked Calendar/announcement/items, while `AssignmentToolUtils.removeNonAssociatedExternalGradebookEntry` tries to preserve external items used by other assignments. No blanket cascade or rollback guarantee is claimed.

**Remote interfaces:** [GradesController](../apps/sakai/webapi/src/main/java/org/sakaiproject/webapi/controllers/GradesController.java) has `GET /api/sites/{siteId}/grading/item-data`, `/categories`, `/grades` and score `POST /grades/{gradingItemId}/{userId}`. They use native sessions, different permission/report shapes and group Gradebook branches; not the proposed delegated setup route. [GradebookNgEntityProvider](../apps/sakai/gradebookng/tool/src/java/org/sakaiproject/gradebookng/rest/GradebookNgEntityProvider.java), prefix `gbng`, is frontend support, not general item/category CRUD. [SakaiGradebook SOAP](../apps/sakai/webservices/cxf/src/java/org/sakaiproject/webservices/SakaiGradebook.java) exposes grade-scale creation/update, not the needed item-create contract. A complete remote interface for desired category/item mutation was not established.

**Confirmed existing seeding:** native Wicket import created 35 independent items across five sites, with seven singleton weighted categories per site. That was a dataset mapping for item percentages, not a production category design. CSV EIDs, blank future scores, released/counting flags and category readback were verified; general drop/extra-credit/calculated course-grade semantics were not. Reference [integration guide Gradebook findings](SAKAI_INTEGRATION_GUIDE.md#gradebook--gradebookng), [ImportExportPage](../apps/sakai/gradebookng/tool/src/java/org/sakaiproject/gradebookng/tool/pages/ImportExportPage.java), [GradeImportConfirmationStep](../apps/sakai/gradebookng/tool/src/java/org/sakaiproject/gradebookng/tool/panels/importExport/GradeImportConfirmationStep.java), [GradebookNgBusinessService](../apps/sakai/gradebookng/tool/src/java/org/sakaiproject/gradebookng/business/GradebookNgBusinessService.java) and [SettingsCategoryPanel](../apps/sakai/gradebookng/tool/src/java/org/sakaiproject/gradebookng/tool/panels/SettingsCategoryPanel.java). ### Assignment ↔ Calendar

**Partially confirmed — source:** native `AssignmentAction` integrates a due event only when posted, the check-add-due-date option is true and the configured calendar exists. `asn.due.date.to.calendar.default` is a UI default, not a universal service hook. The event is zero-duration `Deadline` at dueAt. It stores `NEW_ASSIGNMENT_DUE_DATE_SCHEDULED` and `ResourceProperties.PROP_ASSIGNMENT_DUEDATE_CALENDAR_EVENT_ID` on Assignment; Calendar fields include `CalendarConstants.NEW_ASSIGNMENT_DUEDATE_CALENDAR_ASSIGNMENT_ID` and `EVENT_OWNED_BY_TOOL_ID`. Group assignments produce group events. UI edits remove/recreate the linked event; additional calendar integration is conditional on deployment/initialization. Native deletion uses the stored association. The SOAP assignment helper adds a deadline without these same links.

Thus **Assignments can populate Calendar, but neither raw add nor every creation path automatically does it correctly**. The proposed assignment coordinator must honor `calendar_deadline=course_calendar|none`, create at most one owned event and persist both links. Never call generic `create_calendar_event` afterward for that deadline. No Calendar or permission must be reported as missing/forbidden before posting if a deadline was required, not silently skipped. Do not initialize/create a backing calendar as an unannounced read side effect.

[CalendarService](../apps/sakai/calendar/calendar-api/api/src/java/org/sakaiproject/calendar/api/CalendarService.java), [Calendar](../apps/sakai/calendar/calendar-api/api/src/java/org/sakaiproject/calendar/api/Calendar.java), [CalendarConstants](../apps/sakai/calendar/calendar-api/api/src/java/org/sakaiproject/calendar/api/CalendarConstants.java) and [BaseCalendarService](../apps/sakai/calendar/calendar-impl/impl/src/java/org/sakaiproject/calendar/impl/BaseCalendarService.java): resolve main calendar, `allowAddEvent`, `getEvents`, `addEvent`, edit/commit and `calendar.new`/read/revise/delete permissions. Resource property constants live in [kernel ResourceProperties](../apps/sakai/kernel/api/src/main/java/org/sakaiproject/entity/api/ResourceProperties.java).

**Confirmed seeding:** `/sakai-ws/soap/sakai?wsdl` `SakaiScript.addCalendarEvent(sessionid, sourceSiteId, startTime, endTime, startIncluded, endIncluded, displayName, description, type, location, descriptionFormatted, recurrenceFrequency, recurrenceInterval)` writes `/calendar/calendar/{siteId}/main`; times milliseconds, no recurrence uses XML nil, return is `success`, **not event ID**. Reads: `GET /direct/calendar/site/{siteId}.json?firstDate=YYYY-MM-DD&lastDate=YYYY-MM-DD&detailed=true`. [CalendarEventEntityProvider](../apps/sakai/calendar/calendar-tool/tool/src/java/org/sakaiproject/calendar/entityproviders/CalendarEventEntityProvider.java) supplies site/my/event reads, not generic create. Merge behavior is optional; use site main calendar for initial context, disclose no personal/merged/external calendars searched. Prior initialization via a tool visit succeeded, but headless new-site behavior is unverified.

### Assignment ↔ Announcement

**Partially confirmed — source:** native `AssignmentAction.integrateWithAnnouncement` optionally creates/updates an open-date announcement when posting and auto-announce is enabled. It records `assignmentReference` on the message and announcement ID on Assignment, handles groups and notification levels. This is an alternative native workflow, not unavoidable AssignmentService behavior. Its method name does not prove a scheduled announcement contract. Native auto-announcement and separate Skill announcement must not both run.

**Existing MCP exact contract:** `create_course_announcement(course_id: str, title: str, body: str) -> {"announcement": {"id": str, "courseId": str, "title": str, "postedAt": epoch_milliseconds|null}}`. Required strings; Python/Java enforce nonblank title ≤200 characters and body ≤10,000. The generated SDK schema comes from this signature and does not express every length rule. The contract artifact expresses these bounds as a design clarification; it does not change the existing tool. The write output preserves camelCase/raw timestamp, unlike the read tool's normalized `posted_at` and body.

[Server](../services/mcp/src/sakai_mcp/server.py) → `SakaiClient.create_course_announcement` → `POST /api/mcp/v1/courses/{siteId}/announcements` → [McpAnnouncementWriteController](../apps/sakai/webapi/src/main/java/org/sakaiproject/webapi/mcp/McpAnnouncementWriteController.java). Requires authenticated current user, visitable course and main channel, then `channel.addAnnouncementMessage` checks `annc.new`. It escapes HTML, sets draft=false and author=current user, commits immediately and returns 201/object ID. It uses `commitMessage(edit)` and exposes no selectable email notification level; do not promise email delivery. No attachments, group targeting, scheduled release, explicit Assignment linkage or durable idempotency key. Keep native auto-announce disabled in the coordinator and call this tool after successful posted setup only when immediate announcement is approved. A future-open assignment can be announced now with future-tense wording; announcement “on Monday” needs a separately designed scheduled capability.

Verification uses `get_course_announcements(course_id, cursor?, limit?)`: page through matches by returned ID. Source cap 50, pages do not overcome it. The documented age-filter integer overflow can exclude older messages; absence is not proof of failed creation. A larger lookback alone is not a fix. See [integration guide](SAKAI_INTEGRATION_GUIDE.md#announcements). Separately consider an authorized by-ID read, scheduled announcement/notification contract and marker-backed reconciliation; do not silently replace V1.

### Resources and the attached PDF

Assignment model attachments are ContentHosting references, not local paths/bytes. [ContentHostingService](../apps/sakai/kernel/api/src/main/java/org/sakaiproject/content/api/ContentHostingService.java) supplies `getResource`, content permissions and `addAttachmentResource`; [ContentHosting SOAP](../apps/sakai/webservices/cxf/src/java/org/sakaiproject/webservices/ContentHosting.java) supplies the historically used `createContentItem`. `Assignments.addSubmissionAttachment` concerns a student's submission, **not** an assignment brief. Initial schema supports existing same-course `/content/...` resource references only; verify resource context/access and student access after release. Do not accept arbitrary URL/local path or fetch remote content in Java. Binary PDF upload, storage quotas, access timing and orphan cleanup need a separate bounded upload capability before “attach this local PDF” is supported. Reading the supplied PDF into instructions is sufficient for the base example if no attachment is requested.

## Contract rules and error design

The linked JSON artifact contains recommended `inputSchema`/`outputSchema` pairs and shared `$defs`; `$ref` values resolve against that artifact. A future MCP registration should dereference or supply definitions within each tool schema. There is no executed implementation behind these schemas.

- IDs are opaque strings, including numeric Gradebook/category IDs serialized as decimal strings. Validate/convert them only inside the adapter. Never substitute a title for an ID. JSON `format` alone is not runtime validation.
- Instants require RFC3339 offsets; an explicit IANA `timezone` must agree with those offsets at each instant. Store UTC Instants, render using the approved timezone, reject ambiguous/nonexistent local DST times rather than choosing silently. Sakai's timestamps do not establish a canonical site timezone. Proposed context returns nullable timezone with provenance `site_policy|user_preference|server_default|unknown`; site policy mapping is unresolved. Do not label user preference as course policy.
- Require all scheduling, submission, resubmission, publication and grade integration choices on a write; no silent academic defaults. `instructions` are sanitized HTML (or escaped plain text prepared by the adapter), bounded to 100,000 characters initially; title ≤200. Bounds are proposed and need storage/load acceptance. Resource list ≤20. No source content in logs. Disabled resubmission requires `count=0, until=null`; enabled resubmission requires a finite `until`. Persist the selected write timezone as project-owned Assignment metadata so promotion/readback does not depend on a changed user preference. Context includes a digest of persisted sanitized instructions for result/readback comparison; sanitization fidelity needs native-content acceptance tests.
- `gradebook.mode=new_external` requires same-site category when categories apply, explicit release/counting flags; category omitted only for no-category mode. `mode=none` has no category/flags. Category weights remain unchanged.
- Draft create requires Gradebook mode none and calendar none. Subsequent promotion receives the approved Gradebook/Calendar configuration; no speculative pending link is passed off as a live item. Read output distinguishes draft, posted_future, open, closed using draft and timestamps; raw flags remain included because status alone loses visibility/late-window details.
- Publish requires `expected_assignment_revision` from context; derive opaque revision from current assignment modification/configuration (not an approval token). Recheck native relationships, permissions, category and duplicates immediately before mutation. A revision match is not a cross-service lock; detect concurrent edits in the coordinator and report conflict. Do not silently overwrite an existing posted item with new publish settings.
- Context returns all **visible metadata within permission scope**, including drafts, not filtered by calendar window. The window filters only calendar events. Both window bounds supplied or both absent; absent defaults to today−14 through today+42 days in the resolved display timezone. Max 90 days. Assignment/item/category collections bounded initially at 500 each and calendar at 500; reject over-budget/oversize with actionable validation rather than return an empty/truncated complete response. `complete=false` plus section `unavailable|permission_scoped` reasons forbids claiming no conflicts. There are no student grades/submissions in context.

### Errors and partial results

Reuse current `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_ERROR`, `CONFLICT`, `RATE_LIMITED`, `DEPENDENCY_UNAVAILABLE`, `AMBIGUOUS_WRITE_OUTCOME`, `INTERNAL_ERROR`. Propose `UNSUPPORTED_CAPABILITY` and `PARTIAL_SUCCESS` for this phase with structured details `{stage, reason, retry_safe, known_ids, remaining_steps}`. Never expose exception text, SQL, token, identity or another site's object. Unknown course vs inaccessible course may intentionally share NOT_FOUND.

`reason` distinguishes invalid date/precision, title/external-ID duplicate, category ownership/drop mismatch, missing tool/backing object, unsupported group Gradebook/submission mode, stale revision and permission failure. A known partial result is different from lost response: draft known + grade item known + calendar failure should return a structured result `outcome=partial`, IDs, verified state and remaining work; no announcement. A partial result always returns `assignment_id`; its full `assignment` object may be null if complete readback fails. Its `failure` identifies stage/reason and safe recovery classification. A timeout after POST without IDs remains ambiguous. Extend Python handling to parse known partial responses before reducing to a bare code; do not hide committed identifiers in an HTTP 5xx string.

### Duplicate handling and justified idempotency boundary

Initial design adopts the V1 conservative rule: **one POST, no automatic replay**. Lookup before create catches accidental existing titles/items; it is not durable idempotency. Gradebook enforces external ID uniqueness, so the same known Assignment reference can reconcile its single external item. Assignment title is not a stable key or a reliable site-wide uniqueness constraint; neither title/body nor timestamps alone prove which request created an object.

Retain IDs and exact approved configuration in the workflow's operation record, outside audit content logs. After partial success, read known IDs, resume only missing integrations through `publish_assignment`, and never rerun create. Published replay is a read-verified no-op only when the requested configuration is identical and all ownership links match; changed request is CONFLICT. A partial promotion may leave a draft or a posted assignment; report observed state rather than assuming rollback.

If create response is lost before an ID is known, inspect context and do not automatically adopt/delete/recreate a title match. Report ambiguous outcome and require deliberate reconciliation. Concurrent duplicate-title creates remain a known limitation. A durable principal/site/request-bound operation marker and atomic uniqueness mechanism would justify automatic retries, but Assignment properties alone cannot prevent two concurrent first creates. Defer automated retries until a tested durable record/locking design is implemented; process-local locks are inadequate for multiple replicas. No model-selected “idempotency key” is added merely to promise safety.

### 2. `create_assignment`


Native add persists a skeleton and defaults draft=false, so “immediately set” is not by itself a safety guarantee. ### 3. `publish_assignment` and its coordinator

Purpose: promote a known draft or resume its explicitly approved setup; prevents restarting create after partial failure. Schema: `recommended_tools[2]`. Proposed route `POST /api/mcp/v1/courses/{siteId}/assignments/{assignmentId}/publish`. Shares Python and Java files/services from create; no arbitrary editor.

Sequence: visit + asn.revise + site-wide audience + revision/configuration/owner checks → check all requested integration permissions → reconcile persisted external item and Calendar links → create only missing owned integrations → persist bidirectional properties → verify linked configuration → set draft=false last → apply requested grade-item release/counting → reread Assignment and links → return verified IDs/state. This is a coordinator sequence, not a transaction guarantee. Stage external item unreleased immediately; characterize its default released=true interval and whether staging/transaction can prevent visibility before the Assignment. Calendar event can become visible before final post if commit is separate; avoid claiming full atomic publication and test this interval explicitly. Do not suppress partial failure or publish early to hide it.

For external item use `addExternalAssessment(uid, siteId, assignmentRef, null, title, points, dueDate, assignmentToolId, null, false, categoryId, assignmentRef)`, then read its numeric ID; apply a full DTO through `updateAssignment` for release/counted flags and preserve owner metadata. Treat points/category/title mismatch on an already owned link as CONFLICT, not silent overwrite. Do not attach an unrelated existing external item. Persist revisions after integration changes and use a fresh observed revision for a subsequent recovery call.

A posted identical replay may return verified unchanged outcome; do not generate a second event or reannounce. A different posted configuration requires a future update contract. If draft state has partial links, `gradebook.mode=none` or calendar none cannot silently discard them; conflict and review. The agent must reapprove any material changed recovery plan; a retry of the same approved missing steps may use existing approval subject to host policy.

Unit: stale revision, ownership mismatch, missing backing objects, existing exact links no-op, other-tool external ID denial, failure at each stage including final post/flag update, output not falsely complete. Integration: same known draft resumed twice, concurrent promotion, deleted/wrong category, cross-site Assignment ID, Student/TA denial, draft link visibility interval, one Calendar deadline and one item. Manual: promote a draft in native UI afterwards and compare linkage compatibility; normal native edit/delete in an approved disposable fixture to characterize synchronization/cascade, never as workflow rollback. Unresolved: transactional boundaries, exactly-once concurrency, draft visibility issue below, final flag update ordering.

## Unresolved gates before implementation/release claims

1. **Draft construction/privacy:** raw Assignment add defaults draft=false and persists immediately. Additionally, `AssignmentServiceImpl.isAvailableOrSubmitted` has a source condition where the open-date branch is outside the `!draft` conjunction because of operator precedence. List filtering subsequently checks draft ownership, but by-ID/service paths require explicit tests. Do not claim draft staging guarantees secrecy until checked/fixed in a separate source change.
2. **Transactions/visibility intervals:** characterize Assignment/Gradebook/Calendar/Task commits and event/notification behavior. External item default released=true and Calendar commits can briefly expose partial setup; test or implement safe staging rather than promising atomic rollback. Establish permission checks outside trusted external methods.
3. **Native linkage parity:** prove owner/reference/property persistence survives native edits, draft promotion, delete and reimport; do not blindly reproduce UI swallowed exceptions. Confirm flags on external items can be set through full permission-checked DTO update without clearing ownership.
4. **Remote/runtime parity:** SOAP source is not an exercised full contract; no new delegated mutations tested. Selected runtime may differ from checked-out source. Keep transport within authenticated filter namespace.
5. **Context completeness:** another instructor's hidden drafts, group metadata scope, calendar omission, cross-service observation races and realistic bounds/load must be characterized. No global “no duplicates/conflicts” claim on incomplete context.
6. **Timezone and null-close:** canonical course policy property is not established; return provenance and resolve with instructor. Open-ended accept-until is excluded pending null-safety/student tests. Resubmission effective deadlines need native readback.
7. **Existing-item association:** UI supports it, but score ownership/sharing/maxima semantics remain out of initial slice. Never promote independently imported synthetic marks into native Assignment submissions or links.
8. **Upload/scheduling:** local PDF upload and timed/email announcement need separate bounded capabilities. Existing immediate post remains useful and reusable.
9. **Ambiguous outcomes/concurrency:** no durable request record/atomic uniqueness or exactly-once guarantee. By-ID setup reconciliation and eventual marker-backed operations should be designed only when automated recovery is requested.
10. **Host approval and announcement readback:** Phase 25 real-host approval matrix is open; age filter/cap can prevent proving absence. Do not expand enabled writes or treat absence as permission to recreate.
